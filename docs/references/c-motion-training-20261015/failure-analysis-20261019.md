# 站立外力扰动训练失败分析（2026-10-19）

- 问题：为什么 v0.3–v0.5 的推扰训练未达到 3N×0.3s 满额率 ≥80%，以及今天 v0.9 去 EMA 后为何再次崩溃。
- 范围：本项目自建 MuJoCo/SB3 仿真；源码基线 `bf9a977`，历史站立快照 `1e80d44`。只读核对源码、Git、已有 checkpoint 元数据和历史文字；未运行训练、策略回放、新评估或硬件操作，未修执行逻辑。
- 证据文件：[checkpoint 元数据摘录](checkpoint-metadata-20261019.json)。只保留 JSON 白名单字段、时间和 SHA-256；不保存权重、序列化对象或完整系统信息。历史指标见 [research.md](research.md) 后半部分，现行接口见 [training/README.md](../../../training/README.md)。

## 1. 结论与失败定义

**目前证据支持“观测与动作接口存在缺陷，训练迁移和评估又混入了多个变量”，不能支持“3N 物理不可达”或“架构已经穷尽”。** 最该优先排查的是策略看不到机身运动速度、拿到的 EMA 状态晚一拍，以及所谓平滑惩罚实际比较了 raw action 与上一 filtered action。其因果贡献尚未做单项对照，不能认定某一条是唯一根因。

历史汇总中的 v0.3c：3N×0.3s 满额率 **50%，恒零基线也是 50%**，原定 ≥80% 未达。响应比 11.4×、4N 满额率 25% vs 基线 0%、无扰 10/10 均只剩文字汇总，缺逐场轨迹与完整评估配置。它们可以作为进一步排查的线索，不能提升为普遍主动恢复或鲁棒平衡已通过的结论。4N 的样本数、方向及 seed 未保存，不能补写成 5/20。

今天 v0.9 的历史文字记为无扰存活 0–20%、3N≈0；checkpoint 内最近 100 个训练回合平均只有 **69.62 个控制步**，满 500 步 0/100，支持训练末段很差。该缓冲区是训练尾部样本，**不是本轮重新评估结果**，也不能证明去掉 EMA 在所有配置下必然失败。

## 2. 与站立失败最相关的代码事实

| 问题 | 直接证据与影响 | 目前可下的判断 |
|---|---|---|
| 观测缺少机身角速度和水平速度 | `1e80d44:training/duckstand/env.py` 156–159：45 维仅有重力方向、关节角/速与动作；`train.py` 使用普通 `MlpPolicy`，没有观测历史。相同倾角可能正在倾倒，也可能已在回正；单帧重力方向分不清 | 确定的观测缺项；很可能削弱抗推恢复，但尚未隔离量化其贡献 |
| 观测中的 EMA 状态晚一拍 | 同快照 `step()` 193–226：先更新 `_action_filtered` 并推进物理，再 `_get_obs()`，最后才赋 `_last_action = _action_filtered`。下一次决策看到新物理状态，却仍带旧滤波状态；当前版本顺序相同 | 确定的状态时序缺陷，带记忆的滤波器状态未正确暴露给无历史策略 |
| 平滑惩罚与名称不一致 | 同快照 `action_rate = mean((action - prev_action)**2)`，`action` 是当前 raw action，`prev_action` 是上一 filtered action | 它不是相邻 raw action 差分，也不是相邻 filtered action 差分；持续改变目标也会受罚 |
| 直接续训改变了动作含义 | 历史记录 v0.3b/d 将 scale 从 0.1 改 0.3；v0.4 同时移除 EMA、加入斜率限制、改 scale/std，再从 v0.3c 续训 | 相同策略均值的目标偏移扩大 3 倍，去 EMA 又改变响应动态；只压探索 std 不能保留原确定性行为。多变量迁移失败不能单独归因于噪声 |
| 没有由易到难的推扰课程 | `_sample_push_schedule()` 固定抽样 1–4N、0.2–0.4s、各方向、每回合 1–3 次；参数没有随训练进展变化 | 随机化不等于课程。较难样本可能大量提前结束，HOME/小动作/平滑偏好又可能维持被动稳定局部最优；这是强假设，非已证主因 |

令 raw action 为 `a_t`、滤波状态为 `f_t`，EMA 为 `f_t = αa_t + (1−α)f_(t−1)`。现有惩罚比较 `a_t−f_(t−1)`，因此

`mean((a_t−f_(t−1))²) = mean((f_t−f_(t−1))²) / α²`。

当 α=0.25 时，同一滤波动作变化对应 **16 倍平方惩罚**。这不是说权重必然应除以 16，而是必须先明确希望惩罚 raw 变化、filtered 变化还是滤波跟踪误差，才能比较有/无 EMA 的训练。原先把该项描述成“EMA 后动作天然平滑，所以平滑约束已经解决”不成立。

另一个确定的实现问题是把 **motor 的 `ctrlrange=±0.94 N·m` 用来裁剪目标角 rad**（`env.py` 的 `target = np.clip(...)`；[模型](../../../training/models/duck_v0.xml) 18 行），量纲错误。scale=0.1 时目标范围不触发这层裁剪，不能用它解释 v0.3 的主要失败；scale=0.5 时部分关节可触发，影响后续大动作/行走实验。物理关节自身有限位，不等于这里已正确按关节角限位裁剪。本轮仅记录，未修代码。

## 3. 为什么旧“不可达证明”必须撤回

1. **脚没有被锁住。** 自建模型使用躯干 `freejoint`、各关节 hinge 与地面接触，没有 weld/equality 锁脚；站立任务也没新增锁脚约束。奖励可能偏好 HOME、小动作和低抖动，但这与机械约束禁止跨步不同。换速度任务不能据此宣称“释放了原先被钉住的脚”。
2. **冲量估算漏掉了地面。** `3N×0.3s / 0.73724318kg = 1.2208m/s` 是忽略接触冲量的自由质点速度增量；接地机器人还受地面反力与摩擦，不能把此值直接当整机实际速度。`sqrt(h/g)` 是理想倒立摆时间尺度，不是固定 0.11s 摔倒期限。
3. **支撑域被过度简化。** 按自建模型 HOME 几何，双脚支撑包络约为 x∈[−0.0204, 0.0340]m、y∈[−0.0624, 0.0624]m，具有方向性；不能所有方向都取“半宽 0.02m”。这些是模型几何推算，不是真机实测或动态可恢复域。
4. **EMA 不是固定死延迟。** 50Hz、α=0.25 的等效时间常数是 `−0.02/ln(0.75)=69.5ms`，100ms 内阶跃响应已达到 `1−0.75^5=76.3%`。先前“纯 60ms 延时导致必救不了”的论证不成立；EMA 与斜率限制器也不等价。

因此撤回“3N 不可救”“任何噪声水平都学不出安静站”“必须跨步任务/数周工程/MJX 才可突破”的定论。**撤回不可达证明不等于已证明当前模型一定能达标**；可达性仍缺同配置、同场景的可靠对照。

## 4. 现有评估能说明什么

- [eval_push.py](../../../training/scripts/eval_push.py) 的实际测试集是 **5 个时刻×4 个方向，全为 3N×0.3s，共 20 场景**；每场 `reset(seed=0)`。旧注释“2–4N 网格”已更正。初标定的 8 方向 3N=12% 与此处恒零 50% 不是同一测试集，不能用作训练提升前后对比。
- “满额”仅表示运行至少 500 个控制步（约 10s）未触发宽松的摔倒终止阈值；没有检验最终站姿、速度收敛、恢复时间或位置偏移。动作响应比仅表示动作输出变化，平稳段接近 0 时可成为 `inf`，不等于有效恢复证据。
- [eval_walk.py](../../../training/scripts/eval_walk.py) 的“每档 5 回合”也全用 seed=0；速度档存活 100% 是**无推扰**结果，不能与站立带随机推扰的 35–50% 直接比较。其 reset 后覆写命令却没重算首步观测；当前 49 维环境还未在 reset 重置 `_phase`，使相位沿前一回合延续。两处均未修复。
- 当前环境是 49 维；历史站立策略为 45 维、早期行走为 47 维。不能直接载入现环境重放并称为同一策略复验；维数相同也仍需核对模型、观测语义、scale、EMA 与奖励。

## 5. 后续行走实验混杂，不能反推站立根因

`ab5d9c6`、`996e26d` 的已提交环境快照确实把命令抽样写进了行尾注释，`_vx_cmd` 保持 0。由于没有逐次运行环境快照，不能断言每次运行都是这份代码；但现有证据已经不足以维持“非零命令训练后仍不走，所以算力/命令范围均已证伪”的说法。

v0.8 同时修命令、加入相位观测和相位奖励，不是“只修命令”的对照，故不能推出“命令 bug 非根因”。v0.9 去 EMA 后表现很差，也只说明该次配置失败；观测时序、动作惩罚、初始化与优化条件仍未拆开。v0.4/v0.4b 的 checkpoint 末 100 训练回合平均分别为 **63.95/37.85 控制步**、满 500 步均 0/100，与崩溃记录相符，但没有证明无 EMA 方法普遍不可学。

并行规模变化也不是纯算力对照：8×512 的每批采样为 4096 步，512×128 为 65536 步；batch 从 512→4096，单环境片段从 512→128，策略更新频率随之变化。checkpoint 的 `n_epochs=5`、`gamma=0.99`、`gae_lambda=0.95` 相同，不能抵消这些优化差异。因此不能排除超参和优化过程问题，也没有依据要求直接重写 MJX。

## 7. 若继续，先做什么

1. 先冻结 v0.3c 权重与可重建环境的契约；缺失的环境配置明确记录为待恢复，别直接在当前 49 维环境评估 45 维策略。

## 8. CPU 物理计算的位置及其与失败的关系（2026-10-19 补充）

用户追问：当前物理计算是否在 CPU 上，这是失败关键吗，是否发生在“物体状态计算”这一步？本节依据 `b4268eb` 的源码静态核对，未运行性能测量或训练。

**是，物理计算发生在仿真状态推进阶段；当前使用 CPU 上的原生 MuJoCo。CPU 可能限制采样吞吐，但尚无证据把它认定为此次失败的关键原因。**

| 环节 | 当前实现与运行位置 | 作用 |
|---|---|---|
| 策略输出动作 | SB3/PyTorch 的 MLP；CPU 或 GPU 取决于设备选择及 CUDA 可用性 | 根据观测给出关节目标偏移 |
| 动作变成控制输入 | NumPy/CPU：EMA、目标角与 `_motor_torque()`；设置外部推力 | 生成各关节力矩与躯干外力 |
| 物理状态推进 | CPU：`mujoco.mj_step(model, data)` | 处理碰撞、接触与摩擦约束、动力学求解和数值积分，推进位置、姿态及速度 |
| 形成下一次输入 | NumPy/CPU：`_get_obs()`、奖励和终止判定 | 从仿真状态取出策略可见信息，形成训练样本 |
| 积累一批样本后更新策略 | SB3/PyTorch；CPU 或 GPU | PPO 优化网络参数，不承担物理状态积分 |

源码定位：[env.py](../../../training/duckstand/env.py) 的 `step()` 224–229 行先在循环内算力矩并调用 `mj_step()`，再提取观测；[模型](../../../training/models/duck_v0.xml) 的 timestep 为 0.002s，`DECIMATION=10`，因此**每次策略动作推进 10×2ms=20ms 仿真时间，即 50Hz 控制、500Hz 物理积分**。一次 10s 仿真约需 500 次控制动作、5000 次物理推进（当前截断实现存在一控制步的偏差，此处只说明名义时间尺度）。

这里必须区分**仿真时间**和**现实耗时**：当前离线同步训练循环没有按真实时钟丢步或跳过控制的机制。即使 CPU 花 100ms 才算完上述 10 个物理步，机器人也只前进 20ms 仿真时间；不会仅因为电脑慢，就把相同策略的反应延迟额外增加 80ms 仿真时间。当前代码每步等待求解完成，算得慢首先表现为训练需要更久。

[train.py](../../../training/train.py) 的 `device="auto"` 只控制 PyTorch 网络设备。环境数 ≥32 时启用 `SubprocVecEnv`，512 个环境仍是 CPU 上的多个 MuJoCo 进程，并不等于 512 个 GPU 物理环境。GPU 上的策略网络也不能自动把 `mj_step()` 变成 GPU 求解。

在固定现实时间预算下，采样吞吐较低可能减少可收集的经验和可尝试的方案，从而间接影响收敛机会；不过目前没有分段计时，不能确定主要耗时在物理求解、Python/进程通信还是网络计算。GPU 批量物理后端（例如 MJX）可能改善大批量吞吐，但需要适配环境与数据流，收益取决于模型、批量和硬件；后端迁移还须保持时间步、接触、执行器和奖励语义，不能假定数值完全相同。

本轮判断：先处理已发现的观测/动作接口和训练对照问题；若随后遇到训练周转慢，再按实际耗时决定是否迁移 GPU 物理后端。当前没有新的性能瓶颈实测，也没有证明 GPU 物理能使 3N 抗扰目标自动达成。
